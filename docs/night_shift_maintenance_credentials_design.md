# Maintenance credential/bootstrap design — offline candidate, NOT provisioned

This follows the [pipe review](night_shift_pipe_security_review.md) and
[memory-only TLS prototype](night_shift_maintenance_tls_prototype.md). It records
read-only observations and a proposed credential boundary. It does not authorize
key generation, credential storage, media creation, ACL changes, KVP access or
publication, a new service, VM operation, helper deployment or an inspection retry.
Gate A remains unrun. V1/V2 and all permanent claims/evidence remain retained.

## 1. Observed media boundary

An unelevated local read-only owner/DACL review on 2026-10-18 inspected only the
existing general-launcher receipts directory, V2 workspace root, exact retained
workspace/control sibling, `maintenance.iso` and `working-copy.vhdx`. It did not
read a private key, mount anything, rehash the ISO/source, or query/start a VM.
These ACL snapshots are observations, not a new protected execution receipt or
current launch attestation.

- The general receipts directory has SYSTEM/Administrators FullControl plus
  operator read/execute. That is suitable for reviewed non-secret receipts, not
  the stricter new private-key profile proposed below.
- The retained V2 workspace root/control sibling have SYSTEM/Administrators and
  operator grants. The actual VM workspace additionally has `VmWorkerProcess`
  FullControl and VM-group entries, including inherited grants.
- The retained `maintenance.iso` has explicit `0x00120089` read grants for the
  exact VM SID and `VmWorkerProcess`, and an inherited `0x001f01ff` FullControl
  grant for `VmWorkerProcess`, alongside administrative/operator entries.
- The working copy likewise has exact-VM/capability grants and an inherited
  capability FullControl grant.

The capability SID/name binding is documented in the pipe review. Seeing that
ACE does not by itself establish every Windows restricted-token access result
or prove an exploit. It does mean **private-key confidentiality on these media
has not been established**. Do not place new TLS private keys in that ISO,
working disk, VM configuration, output workspace, generic receipts or any store
accepted merely because it was private before Hyper-V touched its ancestors.
No retained ACL will be repaired to retrofit this design.

The existing `image_finalization.media_files` path remains credential-free and
unchanged. This review makes no claim that an ACL snapshot verifies media bytes.
Integrity still needs reviewed bytes, a pinned digest, native file identity,
write/delete-denying input locks and safe ancestors for a future attempt.

## 2. Proposed key separation

| Material | Proposed location | Allowed transfer |
| --- | --- | --- |
| Controller private key | NEW protected host-only secret store, never given to Hyper-V | None to guest/media/receipts/tools |
| Guest server/issuer private keys | Generated by reviewed live recovery code in guest RAM | Never to host, KVP, ISO, target disk or receipt |
| Controller public CA and exact client-leaf pin | Host-controlled public-only recovery seed | Guest may read; integrity must be established |
| Guest public CA and exact server-leaf pin | One bounded guest-originated VM-bound public record | Host may read; provenance must be established independently |
| Public descriptors/fingerprints/status | Protected non-secret evidence | Ordinary operator read is acceptable |

### Host key store: new objects only

The candidate native creation profile is Administrators ownership, protected DACL,
SYSTEM and Administrators FullControl only. It has **no direct operator, VM,
VM-group, `VmWorkerProcess`, Everyone or other capability ACE**. The elevated
fixed worker can use its enabled Administrators token. Public receipts remain
separate; do not reuse the existing receipt writer that deliberately grants the
operator read access.

This reduces accidental ordinary-file exposure; it is not containment against
the operator/host administrator, arbitrary approved elevated scripts, process
memory access by a compromised trusted host, or a compromised hypervisor. UAC
and an ACL model are not a new sandbox boundary. The operator/application and
host/hypervisor administrative trust assumptions must be reviewed explicitly.

Before any real key byte is generated/written: native atomic create-new with its
reviewed owner/DACL, protected/non-reparse ancestors, regular/single-link file
identity, collision refusal, sharing/handle discipline and post-creation security
read-back all need independent validation. Never create a permissive key then
repair it. Never use an old workspace/control/claim or derive secret paths from a
guest/task record. No native key-store authoring is implemented in this batch.

A real host credential factory also needs a reviewed pinned implementation and
runtime dependencies. The development `cryptography` package is not thereby
approved, available or vendored in a protected worker. Do not use certificate
stores, persistent key containers, arbitrary OpenSSL downloads or unreviewed
low-level crypto wrappers as an automatic fallback.

### Guest keys: RAM only is a requirement, not yet a fact

Future trusted live recovery code must generate fresh keys before exposing any
unvalidated target filesystem. It must verify a root-owned private directory on
actual guest tmpfs, regular/single-link key files with restrictive modes, no
source-disk swap/persistence, and appropriate core-dump handling. No target
program/chroot, key material in command arguments, log output or arbitrary guest
path may participate. Pinned ISO/runtime availability and fixed certificate
profiles/roles must be checked first; no package download/install is authorized.

The fresh VM must have both checkpoint controls disabled/read back, no saved
state, restart, migration, host shares or unapproved network path. Host paging,
crash dumps and privileged VM-memory access remain within the declared trusted
host boundary. Do not claim secure memory erasure or that tmpfs alone prevents
all disclosure. Worker timeout does not prove VM/key destruction; uncertain VM
state remains UNKNOWN with the claim retained.

## 3. Public bootstrap candidate: Hyper-V KVP, not the serial pipe

Microsoft documents that Data Exchange/KVP uses VMbus without network adapters,
that Linux uses `hv_kvp_daemon` and pool files, and that custom guest data maps to
pool 1 (`/var/lib/hyperv/.kvp_pool_1`). In the host WMI v2 API:

- `Msvm_KvpExchangeComponent.SystemName` scopes the component to a VM's
  `Msvm_ComputerSystem.Name`.
- `GuestExchangeItems` contains service-produced custom guest items.
- `Msvm_KvpExchangeDataItem.Source=1` means guest-originated custom data. Source 0
  is host-pushed, 2 is intrinsic guest data and 4 is host-only; none is a substitute.
- The documented `Data` bound is 1,024 characters. Data is visible to host and
  guest and can persist/migrate; it is **not a secret channel** or a freshness
  guarantee.

This is a candidate trusted acquisition route under the host/hypervisor boundary,
not a claim the reviewed Ubuntu recovery ISO currently runs/publishes KVP. The
live integration-service/daemon state, publisher behavior, read permissions and
VM association have not been tested. No KVP query/write, pool-file write, service
enablement, guest installation or registry registration occurred in this review.
KVP is distinct from Guest Service Interface; do not enable file-copy/GSI to make
this work. If Data Exchange use is not approved/available, refuse the candidate.

A future fixed host reader must select the exact new VM GUID from its trusted
claim and verify name/owner/configuration and VM association independently. It
must retrieve the designated guest-originated property locally, not search by a
guest-selected VM ID, friendly name alone, wildcard, remote moniker, or a source
flag supplied over the untrusted serial pipe. Bounded item counts/XML sizes,
DTD/entity rejection, strict property selection, unambiguous Source/Name/Data,
provider deadlines and partial/error-state handling remain to be implemented.
A matching GUID/string argument to an offline decoder is not this proof.

The proposed public record has one fixed item name, version, attempt ID, VM GUID,
fixed inspect operation, a compact base64 CA certificate DER and server-leaf
SHA-256. It is bounded to 1,000 ASCII bytes, below the documented WMI character
bound, and to 512 CA DER bytes. It is one value, not a partially assembled set of
items. A synthetic P-256 CA experiment produced 414 DER bytes and an 804-byte
record (1,610 UTF-16 bytes including NUL); other generated profiles must also
fit or be refused. No truncation, split-record workaround or algorithm fallback
is authorized.

The CA and leaf key are generated inside the exact trusted live guest. The host
learns only the public CA/pin through the independently VM-bound route, freezes
that first matching record, and then requires standard mutual TLS, chain/time/
hostname/role checks and exact leaf pins. Guest authentication of the controller
uses public trust material in the integrity-protected seed. There is no private
key on media, no shared bootstrap password, and **no trust-on-first-use from the
serial pipe**. This describes required future provenance, not current attestation.

The public record's CA parse checks are not issuer authentication, self-signature
or validity-time verification, key-possession proof, or a DLP scanner for arbitrary
certificate extensions. The trusted publisher must use a fixed certificate profile
without arbitrary data/extensions, and real TLS must validate the actual chain
and peer pin. Merely decoding a certificate never makes it trusted.

Reject duplicate/malformed/oversized records, wrong source/name/VM/attempt, old
boot data and changed CA/pin. Identical polling of a frozen record is idempotent,
not new authorization. If the guest reboots/changes its key or a bootstrap/TLS
check fails, stop; do not rediscover/retrust a replacement identity. New decoder
objects cannot replace permanent claims, a new boot/VM identity or fresh approval.
No lifetime, expiry or VM-stop guarantee is supplied by KVP or by an in-memory latch.

## 4. This source batch and validation boundary

`maintenance_credentials_prototype.py` contains only:

1. An exact SYSTEM/Administrators-only host-key **ACL model**. Facts are supplied
   by a caller, not read from Windows; ancestor/native token/handle checks are not
   implemented. A model passing is not permission to create/use a real key.
2. A bounded public-record encoder/decoder with in-memory OpenSSL CA syntax/
   shape checks. Direct private-key DER, non-CA and concatenated/trailing data
   are refused. There is no private-key field or arbitrary file/payload writer.
3. A terminal-on-error public-record latch. It neither performs discovery nor
   confers authorization, and cannot provide global one-shot enforcement.

It is an offline companion to the TLS prototype. Existing runners, guest payloads,
PowerShell scripts, deployment bundle list, protected helpers and tools remain
unchanged. No live TLS context is built from KVP and no production key is generated.
The pure functions have no WMI, KVP, filesystem, serial or networking acquisition
backend. Their inputs must never be promoted to authority by a boolean supplied
by a task/model.

The proposed regression tests use synthetic certificates/keys in test-process
memory and modeled ACLs, including the reviewed media-style extra readers. They
must be run after application; preliminary size/CA parsing experiments are not
validation of the new applied module. Model tests are not native private-file
creation/effective-token evidence or a Linux guest result.

## 5. Remaining implementation/approval gates

Before another live inspection, all of these remain required:

- Native host key-store creation/protection and effective-access tests; a pinned
  key factory/runtime; no private material in model/tool-visible outputs.
- Trusted Linux RAM-key generation and bounded pool-1 publication, including
  daemon protocol/layout, whole-file locking, record collision/update policy,
  bounded nonblocking waits and source-disk/no-target-execution guarantees.
  Microsoft example C programs are reference material, not hardened helpers:
  do not execute their unbounded memcpy/blocking-lock samples as privileged code.
- Exact-VM trusted WMI acquisition/freshness, private-key-free seed integrity,
  immutable public pin binding and new claim/boot lifecycle handling.
- Deadline/cancellation-safe host and guest serial adapters plus strict audit
  receipt semantics. TLS authentication does not itself establish image audit,
  unmount, source preservation or VM cleanup.
- Explicit integration-service and host-administrator trust review, fresh VM
  confinement/checkpoint read-back, protected pinned deployment with a deployed
  900-second native execution ceiling, and separate inspection-only approval.

The existing plaintext guard must remain fail-closed. There is no automatic ACL
repair, private-key-in-ISO shortcut, secret transfer over KVP, plaintext downgrade,
permission broadening, registry change, networking enablement, inspection retry or
transport fallback. If KVP provenance/key protection cannot be established,
review a VM-bound alternative separately rather than relaxing these requirements.
Successful inspection, copy-only finalization, accepted publication and real Gate A
lifecycle/cleanup are still separate gates; Gate B/live model work remain blocked.
