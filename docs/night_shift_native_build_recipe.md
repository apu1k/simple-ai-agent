# Fixed validator executable build recipe — uninstalled HOST candidate

**Applied and verified with unelevated compiler/metadata tests; not installed
or executed as a protected operation.** All **65 new tests** pass without skips.
Both fixed executables compile from the actual sixteen repository C# sources
plus an inert generated profile; reflection-only inspection checks metadata
without invoking either Main. The complete **41-module** related selection
passes **3,063 with two skips**, warnings as errors, in two disjoint bounded

The committed pre-application focused baseline passed **261 tests**, warnings

Those are historical baseline results; applied verification is recorded below.

This checkpoint turns the required build references from the
[guardian entry](night_shift_native_guardian_entry.md) into an explicit closed
compiler recipe for the two fixed executable entry points. It consists of:

- `night_shifts/bootstrap_native_build.py`: stdlib-only HOST data reviewer and
  immutable memory-only staging/argv recipe. No file access or execution.
- `tests/night_shifts/test_bootstrap_native_build.py`: pure fault tests and
  ordinary disposable, unelevated compiler tests with an inert profile.
- This component document and a link from the entry document. No roadmap,
  status, preflight, runtime/tool or PowerShell wiring changes.

**This is not a trusted builder, installer, starter, approved profile, complete
load-closure inventory or runnable protected operation. Never execute checkout
code elevated.** No production profile, native binary, input pin, deployment or

executable. No carried Python/catalog/schema/default-launch behavior changes.

## Closed reviewed build DATA

`plan_validation_build(review, source_files=..., toolchain_files=...)` receives
only in-memory data. Its review dictionary has exactly:

- `version`: integer 1, not a boolean.
- `scope`: `reviewed_validator_build_recipe_not_authorization`.
- `windows_root`: bounded canonical local Windows directory reference.
- `staging_root`: bounded canonical local disposable staging reference.
- `guardian_profile`: the existing closed, non-request-specific fixed-reference
  profile. The existing emitter checks SID, anchor identity/path and launch root.
- `source_pins`: independent complete byte count/SHA-256 pairs for exactly the
  sixteen fixed repository C# sources plus `ReviewedGuardianProfile.g.cs`.
- `toolchain_pins`: independent complete byte count/SHA-256 pairs for exactly
  `csc.exe`, `csc.exe.config`, `mscorlib.dll`, `System.dll`, `System.Core.dll`,
  `System.Xml.dll` and `System.Runtime.Serialization.dll`.

The caller's source byte map contains exactly the sixteen repository members.
The profile is generated internally from the existing fixed-reference emitter;
its generated bytes MUST match the separately reviewed profile pin. Caller-
selected profile source, source member names, commands, references, options,
response files, plugins and request/policy pins are not accepted. Case aliases,
missing/extra members, mutable/non-byte inputs, changed bytes and oversized
members refuse. Each source is bounded to 512 KiB; each selected toolchain
member is bounded to 32 MiB. Returned files, commands, environment and pins are
immutable tuples/bytes, not aliases of the caller's mutable dictionaries.

The recipe preserves the existing non-circular ordering: compile independent
anchor/SID/launch references first; independently pin the finished binaries;
only THEN form the outer request that pins those binaries and the private
policy that binds that final request. A changed profile requires separately
reviewed new source/build/binary/request/policy pins. There is no retry/reset.

A matching pin is local byte consistency, NOT review, origin authentication,
secure acquisition, source safety, compiler correctness or authorization. The
module deliberately does not discover current paths, fetch inputs, compute
trusted pins from a checkout, query native state or inspect a host.

## Exact staging and invocations

The staging tree is separate from Windows and from both profile-protected roots;
component-boundary, case-insensitive overlap is refused. The recipe does not
create that tree or prove it is fresh, private, local NTFS or non-reparse.
The future builder must establish these properties independently.

```text
<fresh-private-stage>/
  native_validator_*.cs             # exactly sixteen verified source snapshots
  ReviewedGuardianProfile.g.cs      # verified generated fixed-reference DATA
  validator.manifest                # exact fixed asInvoker / uiAccess=false
  temp/                            # private compiler temporary directory
  out/
    validator-install-guardian.exe
    validator-install-guardian.exe.config
    validator-provision-worker.exe
    validator-provision-worker.exe.config
```

The two `.exe.config` files are the existing exact launch-config bytes already
pinned by the request contract. The manifest is fixed, with no automatic UAC or
self-elevation. A separately trusted starter must supply the required elevated
operator role. Producing an `asInvoker` binary is not proof of its actual role,
pre-load provenance, allowed parent or original deadline.

Both commands select the absolute `Framework64/v4.0.30319/csc.exe` below the
reviewed Windows root and compile all seventeen verified source inputs. They
use explicit absolute references to only the five assemblies listed above.
Fixed options include:

- `/noconfig`: do not consume the compiler's implicit `csc.rsp`.
- `/nostdlib+`: no implicit standard-library reference selection; `mscorlib.dll`
  is an explicit, independently pinned reference.
- `/target:exe`, `/platform:x64`, `/langversion:5`.
- `/optimize+`, `/debug-`, `/checked-`, `/unsafe-`, `/warn:4`, `/warnaserror+`,
  `/utf8output`, `/nologo`.
- The fixed manifest, fixed output path, and exactly one explicit `/main:`:
  `AiAgent.ValidatorEntry.ValidatorGuardianProgram` or
  `AiAgent.ValidatorWorker.ValidatorWorkerProgram`.

There is no shell command, PATH search, MSBuild/project discovery, wildcard,
response file, source fallback, dynamic entry or alternate compiler. The
supplied environment DATA contains only `SystemRoot`, `WINDIR`, `TEMP` and `TMP`;
the last two point to the private staging temp directory. It must replace, not
extend, an inherited environment. In particular no inherited PATH, DEVPATH,
COMPLUS/profiling hooks or user-selected compiler variables are permitted.
No process is created by this module, so enforcement remains the future
builder's responsibility.

The output inventory is exactly the four existing launch names. Debug files,
extra assemblies and diagnostic sidecars are not deployment inputs. This
recipe makes no bit-reproducibility claim: fixed arguments and pins do not
eliminate compiler timestamps, MVID variation or host dependencies.

## Compiler inputs are NOT the full pre-load trust closure

The seven selected toolchain members are an explicit byte-input set, NOT a claim
that these are every file the compiler or CLR can load. `/noconfig` suppresses
`csc.rsp`, NOT `csc.exe.config`, machine configuration or CLR loader policy.
`/nostdlib+` suppresses implicit reference selection, NOT trusted OS/native DLL
loading, CLR activation, GAC/Fusion policy, native images, inherited object state
or Windows side-by-side behavior. The CLR/OS, native dependencies, compiler
configuration, machine policy, compiler directory/ancestry, working-directory
closure and process environment still require independent review/measurement
and secure acquisition before any compiler or produced assembly is loaded.

The produced executables likewise depend on the separately trusted Framework
and Windows closure. Their current fixed `.config` files do not by themselves
exclude every .NET probing, GAC, publisher or machine-policy influence. No
in-process hash check can retrospectively authenticate an already loaded
compiler, assembly, CLR or DLL. These conditions must not be inferred from the
pure data review or compilation tests.

A future separately reviewed builder must hold/reverify the actual input paths
and native identities, bound its own compiler process lifetime, reject occupied
staging/output trees without repair, verify exact artifacts and retain evidence.
It must not execute a plan from an untrusted Python process as an elevated
shortcut. Build/setup work is distinct from the later provisioning attempt's
original runtime deadline and cannot grant it a fresh window.

## Applied verification and honest limits

Pure checks cover closed review/source/toolchain inventories, independent pins,
profile-pin changes, byte bounds, immutable deterministic memory-only output,
path separation/injection, fixed references/options/entries, restricted
environment, exact config/manifest bytes and exclusion from carried/tool wiring.

The Windows-only fixture compiles the actual sixteen repository sources plus
an inert generated profile with both exact compiler argv recipes, in an ordinary
disposable directory, unelevated. The fixture observes installed
compiler/reference bytes to exercise consistency; these are test data, NOT
independent authorization for real builds. CLR reflection-only inspection in a
separate process checks both entry-point declaring types, AMD64/IL-only metadata
and assembly-reference names. Raw PE checks cover the x64 PE32+ header and
embedded non-elevating manifest marker. Negative compiles require refusal
without an explicit Main or without the generated profile. Neither executable
is launched and neither Main is invoked. No native section, token, locking,
job, park, child-absence, provisioning or VM path is exercised.

One test-only repair was needed: PowerShell refuses an undefined zero value
for `ImageFileMachine`. The inspector now initializes that output variable with
valid member `I386`; `GetPEKind` must overwrite it with `AMD64`. It does not
preseed the expected result or weaken the metadata assertion. Before this
repair the new suite had 62 passes and three fixture errors after both positive
compiles had already succeeded. No build-recipe or C# source repair was needed.
