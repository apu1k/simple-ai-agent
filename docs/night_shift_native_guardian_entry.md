## Avoid the executable/request hash cycle

The outer canonical request already includes the guardian and worker executable
pins. Embedding its request hash (or a policy hash binding that request hash)
INTO those same executable builds would make a circular content-pin dependency.
This candidate deliberately does NOT do that.

`build_validation_guardian_profile()` accepts ONLY this closed memory-only data:

- Version 1 and scope `reviewed_guardian_build_references_not_authorization`.
- Exact bounded canonical same-account operator SID.
- Separately reviewed approval-anchor path and NTFS volume/index reference.
- Fixed guardian/worker launch-root path.

It validates the existing narrow path alphabet, canonical numeric/SID ranges,
component-boundary root separation and bounded source length. Output is at most
2 KiB of deterministic ASCII C# with one fixed class:
`AiAgent.ValidatorEntry.ReviewedGuardianProfile.Create()`. No arbitrary source,
source member list, command, plugin, request/policy hash, budget, expiry, reset or
other field is accepted. These are immutable references, NOT observed security,
authorization or proof of pre-load trust. The C# profile constructor independently
checks its shape as well.

There is deliberately **no shipped production profile, dummy default or profile
lookup fallback**. The new entry source requires the separately generated and
independently reviewed profile source to compile. Model tests supply inert data
ONLY in their ordinary disposable compiler directory. No actual operator inputs,
privileged anchor or executable is created by the emitter/tests.

The later reviewed build/install sequence must resolve references WITHOUT a
self-pin cycle:

1. Separately establish/review stable private anchor locations/identities and
   the exact operator. No repair or runtime alternate anchor is permitted.
2. Review the fixed source/load closure and non-request-specific profile;
   build the two fixed x64 executables unelevated under the reviewed compiler/
   dependency recipe. Both compile the required profile and common sources;
   explicit entry selections are `AiAgent.ValidatorEntry.ValidatorGuardianProgram`
   and `AiAgent.ValidatorWorker.ValidatorWorkerProgram`. The separately applied,
   offline-verified [closed build recipe](night_shift_native_build_recipe.md) fixes the source,
   compiler/reference inputs, arguments and explicit entry selections. It is
   memory-only HOST data, not a trusted builder or full loader-closure review;
   its disposable executable-compilation tests do not establish protected
   installation or binary reproducibility.
3. Independently pin the FINISHED binaries/configurations/runtime/code inputs,
   then construct/review the canonical outer request.
4. Separately install/review the private one-attempt approval policy binding that
   FINAL request hash, plus the exact protected build/load closure.
5. A trusted pre-load starter authenticates these inputs, permanently handles
   early-failure/cancellation, arms an independent original-window watchdog and
   delivers the exact request/read capability/metadata to the fixed guardian.

Changing the compiled anchor/SID/root requires a separately reviewed new build
and fresh binary/request/policy pins. It is not a runtime retry option. No production
build, setup, installation or approval-channel implementation is supplied here.

## Fixed incoming frame and approval authority

The incoming argument tuple has exactly ten non-secret fields:

1. `--install-once-section-v1` (worker mode is not accepted).
2. Exact inherited read-only section handle.
3. Independent outer-request byte count, at most 32 KiB.
4. Lowercase outer-request SHA-256.
5. Original budget, 6–900 seconds.
6. Original UTC expiry.
7. Earlier absolute common-machine QPC limit.
8. Matching QPC frequency.
9. Independent canonical policy byte count, at most 1 KiB.
10. Lowercase SHA-256 of the complete canonical policy.

The first eight shapes reuse the existing bounded worker-frame parser after a
mandatory GUARDIAN-mode check on a cloned tuple. The policy fields are strictly
bounded canonical decimal/hash data. This is fixed parser reuse, not a mode
fallback. No root/path/SID, arbitrary command, input file or executable is read
from argv. No credentials or tokens may enter this metadata.

The profile supplies the only approval anchor/identity and operator SID. The
frame supplies consistency pins/window data, NOT approval. The actual existing
approval body must reproduce the canonical expected policy and then acquire and
verify the authentic separately installed private policy through held handles,
consume its fixed permanent claim, and only THEN decode the outer request.
Matching command-line hashes alone cannot substitute for that filesystem-backed
conditional authority. Genuine policy installation, durability, native ACL/NTFS
security and independent review are not established by a generated class.

The native guardian host gate requires x64 Windows, the exact compiled launch
root plus fixed guardian filename and exact enabled operator SID before section
reception. Subsequent native target/process gates still bind the approved actual
request. These are necessary role/consistency checks, NOT retrospective trust in
an already loaded assembly or authentication of an untrusted parent.

Both entries share exactly the existing read-only section operation: exact read
access and inherited-handle flags, bounded map/copy, inheritance removal,
adoption only after section mapping, and checked once-only unmap/close. The
static helper is internal to the reviewed assembly, called only after each fixed
entry's own gate. It is not a public arbitrary-handle/path API or a named-object,
stdin, environment or file-reopen fallback. Native behavior still requires
characterization.

## Original window through approval and worker delivery

Entry construction performs no clock/native work. `Run` is terminal/serialized
before frame parsing. One existing `WorkerClock` guard spans incoming QPC-to-local
translation, approval construction and request reception, so new inner wrappers
cannot forget earlier rollback/nonfinite observations.

The entry conservatively translates the earlier common-counter cap with the
existing receiver algorithm. It constructs the ACTUAL approval owner under that
mandatory cap BEFORE receiving bytes. The new internal approval overload can
only take `min(existing budget/UTC window, earlier cap)`, never renew it. Loading,
argument decoding, reception/close, policy/claim I/O, request/target verification,
publication, worker load and execution all consume the earlier supplied limit.
The parent process core subsequently sends its ACTUAL earlier stop point to the
worker, with all stop reserves INSIDE the same window. Historical APIs without
an incoming cap are unchanged and do not become protected starters.

This preserves a correctly supplied counter cap. It does NOT authenticate its
origin or supply the missing pre-load starter/watchdog. Forged consistency
metadata cannot prove the true original operation start or authorize renewed
time. Actual QPC/clock/CRT/load behavior and bounds on blocking kernel/CLR work
remain unverified; cooperative checks are not hard interruption.

Malformed frame/host/policy-plan failures or input cancellation BEFORE the actual
approval run cannot consume an on-disk claim retroactively. The trusted route
still needs a permanent whole-attempt/early-failure policy. Once authentic policy
acquisition/claim succeeds, malformed/null raw requests are consumed under the
existing claim-before-decode rule. No failure or absent claim grants a retry.
